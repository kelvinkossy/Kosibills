CRITICAL Bugs / Blockers
1. Missing credentials: 'include' on several fetch calls
In Transfer.tsx (line 65), Dashboard.tsx (lines 68, 74), and sub-wallets on update (App.tsx line 471), the credentials: 'include' flag is missing. Since the backend uses httpOnly JWT cookies, these requests will fail with 401 once the user is authenticated — meaning transfers, balance updates, and sub-wallet reads will silently fail.

2. Unauthenticated sub-wallet endpoints
GET /api/sub-wallets/:userId and POST /api/sub-wallets/create have NO authenticateToken middleware. Any user (or script) can query another user's sub-wallets or create wallets by passing any userId — without logging in at all.

3. Password validation mismatch
The frontend (Auth.tsx line 78) validates password.length < 6 to show an error, but the server's Zod schema (registerSchema) requires min(8). This means users get no clear feedback — they can enter a 7-character password, the frontend accepts it, and the server rejects it with a confusing error.

4. CSRF Protection is configured but not applied
csrfProtection middleware is defined (line 669 of server.ts) but never attached to any route. The CSRF tokens are never required — so all POST endpoints are potentially vulnerable to cross-site request forgery.

Security Issues
5. Hardcoded admin email in startup code
Lines 349–352 of server.ts hardcode kelvinnnatu2@gmail.com as admin on every server start. Anyone who knows this email can register with it and potentially gain admin — or the email is just permanently in the code, which is a bad security practice. Admin assignment should be done manually via a secure setup process, not hardcoded.

6. Admin identified by spoofable headers
Several admin routes use req.headers['x-admin-id'] to log who performed an action. HTTP headers can be manipulated — you should use the req.user.id from the verified JWT instead.

7. Potential XSS in admin email send
In /api/admin/send-email, the admin's message is inserted into HTML with only \n → <br> conversion, with no sanitization. A malicious admin could inject HTML/script tags. Use a proper HTML sanitizer or always render as plain text.

8. In-memory 2FA and OTP stores
Both twoFactorStore and otpStore are in-memory Maps. If the server restarts (very common in development), all pending OTPs and 2FA codes are lost. On production, a restart mid-authentication would leave users stuck. Use the database or Redis for these.

9. Default weak secrets fallback
JWT_SECRET defaults to 'kosi-bills-dev-secret-change-in-production' and BVN_ENCRYPTION_KEY to 'kosi-bills-dev-bvn-key-32-chars!!'. While the app warns about this, these are recognizable strings that attackers could use to forge tokens if somehow deployed without the env vars set.

10. Legacy plaintext PIN support is risky
verifyPin supports legacy unhashed PINs with if (!hash.startsWith('$2')) return hash === pin. This means if any PIN record is ever corrupted or manually inserted as plain text, it will compare without hashing — which is a silent security downgrade.

Code Quality Issues
11. Giant single-file backend (3,021 lines)
server.ts does everything: DB init, migrations, auth, payments, admin, support, push notifications. This is hard to maintain and debug. It should be split into modules: routes/, services/, middleware/, db/.

12. package.json name still says "react-example"
The project name was never updated from the template. It should say "kosi-bills".

13. N+1 query in sub-wallets fetch
The sub-wallets endpoint runs membersStmt.all(wallet.id) inside a loop over wallets. With many sub-wallets this becomes slow. Use a single JOIN query instead.

14. setView typed as any in Transfer.tsx
setView: (view: any) => void should use the View type from types.ts. TypeScript is not being used to its full benefit here.

15. @tanstack/react-query is installed but not used
The app installs React Query but all data fetching is done with manual useEffect + fetch. This means no automatic caching, stale-while-revalidate, or deduplication of requests. Either use React Query properly or remove the unused dependency.

16. Duplicate project directories
The workspace contains two full export copies (ReplitExport-kelvinnnatu24-4tarzip and ReplitExport-kelvinnnatu2tarzip). There's also a src/ folder at the root level AND a frontend/src/ inside the 2nd export. These should all be cleaned up.

Architecture Observations
17. SQLite is fine now — plan for scale
SQLite with WAL mode is actually excellent for this scale. The existing indexes are well-placed. If you reach 10k+ concurrent users, migrating to PostgreSQL will be needed — but don't rush this.

18. Firebase is imported but only used for Google OAuth
Firebase is initialized including Firestore, but the app only uses Firebase Auth for Google sign-in. The Firestore initialization generates error logs on every startup. Either fully use Firebase or just use the firebase/auth import selectively.

19. Vite is the proxy in production
The architecture has Express serving both the API and proxying through Vite. For production, you should vite build first and have Express serve the static files from /dist — not run Vite's dev server.

Missing Features Worth Adding
20. Email verification flow is incomplete
The DB has is_email_verified, verification_token columns and the backend sets a token on registration — but there is no backend endpoint to verify the email by token, and no frontend page/flow for it. Users can register with unverified emails.

21. Referral reward system is tracking but not rewarding
Referral codes are stored and linked (referred_by, total_referred columns) but there is no code that actually credits any reward or bonus when a referral signs up. The tracking is there; the reward logic is not.

22. No phone number normalization
Phone numbers are stored as-is. 0801..., +2348..., 2348... could be three records for the same number. You should normalize all phones to a single format on save.

23. Transfer search only works by exact phone
The /api/users/find?phone= endpoint uses an exact match. Users who enter a phone in a slightly different format (with spaces, dashes, or different prefix) won't find the recipient.
